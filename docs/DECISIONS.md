### 疑點二：真實回測數字（總報酬 129.6%／年化 8.0%／Sharpe 0.51）跟 Task 6 報告（92.1%／6.5%／0.39）為什麼不一樣

**完整拆解（用當前程式碼、控制變因逐項重跑，四個組合互相對照）**：

| 版本 | 因子組成 | 回測結束日 | 總報酬 | 年化 | Sharpe |
|---|---|---|---|---|---|
| Task 6 原始報告 | mom_120 在、div_yld=0 | 2026-04-17 | 92.1% | 6.5% | 0.39 |
| 只修正因子（疑點一的修正） | mom_120 移除、div_yld 正式加權 | 2026-04-17 | 97.7% | 6.8% | 0.42 |
| 只延伸資料到今天（原始因子） | mom_120 在、div_yld=0 | 2026-08-28 | 129.6% | 8.0% | 0.51 |
| 兩者都做（Task 8 真實跑出的樣子） | mom_120 移除、div_yld 正式加權 | 2026-08-28 | 136.5% | 8.3% | 0.54 |

**結論很清楚**：129.6% 這個數字**幾乎完全**是資料回測區間往後延伸到
今天造成的（92.1%→129.6%，+37.5 個百分點），跟疑點一的因子問題基本
無關（因子修正本身只貢獻 +5.6 個百分點，92.1%→97.7%，占總差距不到
六分之一）——不是「原因不明」，是可以精確拆解、對得起帳的差異。

**「一週資料」的假設是錯的，實際上是延伸了約 4.3 個月**：Task 6 執行
時 `quant_layer2.py` 的 `END_DATE` 常數寫死在 `"2026-04-17"`，daily_
update.py（Task 8）改用 `data_end=today`，執行當下的「今天」是
2026-08-28，兩者相差 4 個半月，不是一週。

**為什麼 4 個月能造成 37.5 個百分點的總報酬差異——這個解釋站得住腳嗎**：
用真實 TAIEX 資料查證：2026-04-17 收盤 36804.34 點，2026-08-28 收盤
46331.45 點（區間最高到過 47741.51），**短短 4 個月大盤大漲 +25.9%**，
這正是 Task 3/4/6 都已經記錄過的「史詩級大多頭」的延續。用策略自己的
淨值曲線驗證複利計算：策略在這段區間淨值從 1.9208 漲到 2.2956，區間
報酬 +19.5%；把 Task 6 原本的 92.1% 累積報酬（相當於淨值 1.921）乘上
這段 +19.5%，`1.921 × 1.195 = 2.296`，換算成總報酬正好是 **129.6%**——
跟真實回測輸出**完全吻合**，不是約略對得上，是精確複利算出來一樣的
數字。這就是複利的本質：已經漲了 92% 的本金，之後再漲 19.5%，看起來
會比「19.5%」大得多，因為是疊加在已經放大的本金上。

**是否需要重新執行 Task 6**：不需要。Task 6 的原始數字（92.1%／6.5%／
0.39）在它執行的那個時間點（2026-04-17 為止）**完全正確、沒有錯誤**，
只是後來累積了更多真實市場資料。這是任何持續更新的即時系統都會發生的
正常現象（策略淨值每天都在變化，任何「某個時間點」的報告都會隨時間
自然過時），不是 Task 6 的方法或程式有問題，不構成需要重跑整套

真實、永久的程式變更，如果之後要讓 Task 6 報告裡的數字跟目前程式碼

### 疑點三：ML 崩盤預警模型多年 AUC < 0.5，比亂猜還差

完整診斷過程、根因分析、對機制偵測系統影響、最終決定，見新增報告
`reports/ml_alert_reliability_diagnosis.md`（含完整逐年 AUC 表、獨立
事件數拆解、pooled OOS AUC 驗證）。這裡只記結論：

**根因**：不是程式 bug（`predict_proba` 的類別索引順序、機率方向都
驗證正確），也不是單純「模型沒加正規化」（測過加 early stopping，
結果好壞參半、不穩定，無法一致改善）。真正原因是崩盤標籤定義（未來
20 日報酬 < -5%）用滾動視窗製造大量高度重疊、非獨立的標籤——多數年份
只有 1-6 次真正獨立的崩盤事件（2023、2024 甚至只有 1 次），用逐年
AUC 評估這麼少的獨立事件，估計值天生就會在 0.2~0.8 之間大幅擺盪。
把 13 年 walk-forward 的樣本外預測全部合併算一次 pooled AUC：
**0.493**，幾乎正好等於隨機猜測——這是比任何單一年份都可靠的整體
判斷，證實這個 ML 元件目前的樣本外判別力**跟隨機沒有顯著差異**。

**決定**：文件裡誠實記錄這個限制，**不**變更 `regime_engine.py` 的
`classify_regime_raw()` 分類公式（不把 `crash_prob` 從判定條件移除）。
理由：Task 3-6 已經在**這一版**分類公式上完成完整驗收與後續分析，
現在改公式會讓已經定案的一大批數字全部變成「用舊公式算出來」，代價
遠超過這次疑點排查的範圍；`crash_prob` 是跟健康分數／HMM p_bear 用
AND 邏輯合併的其中一票，接近隨機的第三票最壞情況是偶爾多擋/少擋一次
邊界判斷，不是讓整個系統徹底失真。是否要調整三方投票設計，留給你
之後決定，不在這次驗收範圍內處理。

**後果**：新增 `reports/ml_alert_reliability_diagnosis.md`；沒有修改
`regime/ml_alert.py` 或 `regime/regime_engine.py` 的任何邏輯（純診斷，

## 2026-08-23 — Task 6c 後續診斷：策略跑輸 TAIEX 是選股問題還是台積電效應？

**狀態：診斷完成，補充脈絡，原本 Task 6c 的發現完整保留不變**

**問題**：Task 6c 發現策略逐日報酬顯著跑輸市值加權 TAIEX（bootstrap
p=0.0272，年化落後約 7.4 個百分點）。這個負面結果可能有兩種完全不同
的成因：(1) 策略選股能力本身不如大盤的平均表現，(2) TAIEX 是市值
加權指數，這段期間台積電一檔巨型股可能貢獻了大盤報酬中不成比例的
一大塊，導致「跑輸大盤」主要是「跑輸台積電」，不是選股能力的問題。
兩種成因對 README 該怎麼誠實呈現這個發現，意義完全不同，需要先
分清楚。

**做法**（`strategy/benchmark_concentration.py`，真實資料計算）：
1. 用「收盤價×成交量」252 日滾動均值當市值代理（沿用
   `strategy/cta_module.py` 既有的 `build_proxy_market_cap()` 做法，
   本專案資料庫沒有股本/流通股數，無法算出真正市值——這是誠實列出
   的方法論限制，不是為了省事）
2. 用「移除法」（不是權重×漲幅的粗略估算）算台積電對代理指數總報酬
   的真實貢獻：分別跑「含台積電」與「排除台積電、其餘股票權重重新
   正規化」兩個代理指數的真實逐日報酬序列，總報酬的差就是台積電的
   貢獻
3. 額外建立等權重代理指數（不受市值大小影響）
4. 對三個基準（真實市值加權 TAIEX、代理等權重、代理排除台積電）
   各自重新跑一次 Task 6c 的 bootstrap 顯著性檢定，跟原本「vs 真實
   TAIEX」的結果並列比較

**結果（真實計算，2015-2026）**：
- 台積電自身總報酬 +1355.2%，在代理市值加權指數中的平均權重 6.2%
- 代理市值加權指數總報酬：含台積電 +156.1%／排除台積電 +126.6%
  → 台積電貢獻代理指數總報酬 +29.4 個百分點（佔代理指數總報酬的
  18.9%）
- **重要的方法論警訊**：代理指數總報酬（+156.1%）遠低於真實 TAIEX
  官方指數（+296.9%，落差 141 個百分點）——這代表用成交量代理市值，
  系統性低估了台積電這種權值股的真實市值權重（公開市場資訊台積電
  在 TAIEX 官方市值權重長期在 25-35% 左右，遠高於這裡算出的 6.2%）。
  這代表「台積電貢獻 18.9%」這個數字很可能是低估值，真實貢獻比例
  應該更高——但方向性結論不會因此推翻：如果真實台積電權重更高，
  真實的「排除台積電後大盤」報酬只會更低，讓策略看起來更不遜色，
  不會更差
- 策略 vs 三個基準的 bootstrap 檢定：對**真實市值加權 TAIEX 仍然
  顯著跑輸**（p=0.0272，不變）；對**等權重代理 TAIEX 不顯著**
  （p=0.4192）；對**排除台積電代理 TAIEX 也不顯著**（p=0.5074）

**結論**：排除台積電後、以及對等權重大盤，策略都不再顯著跑輸——
這代表 Task 6c 的負面結果主要是「大盤總報酬被台積電這一檔巨型股
撐起來」的集中度效應，不是策略選股能力本身特別差。但這不代表策略
選股能力很好（沒有顯著跑輸不等於顯著跑贏），只是原本負面結果的
主要成因找到了：是被單一巨型股撐起來的基準太難打，不是選股邏輯
本身有明顯缺陷。

**【重要】這個診斷結果不會取代或淡化 Task 6c 已經記錄的發現**：
「策略對市值加權 TAIEX（官方真實指數，這是這個專案／README 應該
使用的標準基準）顯著跑輸，p=0.0272，年化落後約 7.4 個百分點」這個
事實完整保留，不因這份補充診斷而改變。README 的 Limitations 章節
兩者都要寫，不能只挑「排除台積電後不顯著跑輸」這個對策略有利的
半句話，選擇性引用——這正是本專案研究誠信原則要防範的行為。

**後果**：
- 新增 `strategy/benchmark_concentration.py`、
  `reports/benchmark_concentration_analysis.md`
- 新增 `tests/test_benchmark_concentration.py`（5 項，合成資料，
  含移除法在極端案例下方向正確性的驗證），pytest 全部 72/72 通過
- Task 9（README／文件與發布）撰寫 Limitations 章節時，這筆決定裡
  的兩個發現（原始負面結果 + 補充脈絡）都要並列呈現
- 如果之後 Task 7 補充了真實股本/市值資料，可以回來用真實市值權重
  重跑這份診斷，取代目前的成交量代理權重，得到更精確的台積電貢獻
  比例（目前的 18.9% 已知是低估值）

## 2026-08-22 — Task 5 相關澄清：資料範圍延伸、ML 版報酬下降原因

**狀態：澄清記錄，不是待決定事項**

**澄清一：margin_usage 因子失效跟資料範圍延伸無關**——曾經一度以為
「margin_usage／inst_flow 在 Task 2、Task 5 都測不出訊號」可能代表
應該進一步往前延伸資料範圍（更多歷史樣本＝更容易測出訊號）。已澄清

fold）「有機制標籤可用」的資料，margin_usage 連續 9 年排名墊底是訊號
本身穩定地不存在，不是樣本數不夠。真正卡住 Task 3 資料範圍的是
**三大法人（institutional_investors）資料的真實可得起點 2012-05-02**
（見 `docs/DATA_AVAILABILITY.md`），不是融資資料（`margin_trading`
的可得起點更早，2001-01-05，見 Task 1 細節）——這兩個資料集的限制
是獨立的兩件事，融資資料本身並不卡在 2012-05-02 這個門檻上。

**決定**：暫不進一步延伸資料範圍。理由：(1) 延伸資料範圍解決不了
margin_usage/inst_flow 沒訊號的問題（訊號穩定性已經在現有樣本下驗證

應該等 Task 6 的 Walk-Forward（6 fold，2020-2025）結果出爐後，看
樣本外表現是否已經充分，再決定要不要進一步延伸——不要在還沒有
walk-forward 證據之前就先假設「資料不夠多」。

**澄清二：Task 5 端到端比較裡 ML 版總報酬下降、換手率上升的原因**——
`docs/DECISIONS.md`「Task 5：ML 因子合成完成」那筆已經列出數字，這裡
補充明確的原因拆解，避免之後誤讀成程式錯誤：
1. **Walk-forward 暖機期效應**：ML 預測值只從 2018 年才開始有值
   （2013-2017 是訓練資料暖機期，見 `strategy/ml_composite.py` 的
   `MIN_TRAIN_DAYS` 判斷），2015-2017 這段期間 ML 版等於空手／低配置，
   直接拉低「總報酬」這種累計數字，但不影響「年化報酬」對照的公平性
   （年化報酬用幾何平均，天然對齊有效交易天數，且 ML 版年化報酬
   6.8% 實際上略優於基準版 6.5%）。
2. **每年重訓造成的因子組合邏輯逐年微調**：expanding-window walk-forward
   每年 1 月重新訓練一次模型，模型學到的「因子重要性」與非線性組合
   方式每年都會因為新增一年資料而微調（見
   `reports/feature_importance_by_year.md` 的逐年 importance 表格，
   數值確實逐年浮動），這會讓選股結果在年度之間比固定權重的線性版本
   更容易變動，直接反映在換手率（330.2% vs 基準版 255.2%）與年度間
   績效變異度上。**這是「模型持續適應最新資料」與「持倉穩定度」之間
   已知的取捨（adaptability vs stability trade-off），不是程式錯誤**——
   跟固定一套永遠不變的權重相比，願意逐年微調換來的是模型不會固守
   過時的因子關係，代價是換手率與年度間波動變大。

## 2026-08-22 — Task 6 ablation D 語意決定：把 use_regime_weights 拆成兩個獨立開關

**狀態：已決定並實作**

**問題**：Task 4 的 `use_regime_weights` 一個布林開關同時控制兩件事：
(1) 選股排名要不要用機制靜態因子權重（`REGIME_FACTOR_WEIGHTS`，Task 4a）
取代動態 IC 加權；(2) 部位規模要不要用機制建議曝險比例縮放（Task 4b）。
Task 6b 要做 ablation D（ML 選股＋機制曝險），這時候問題浮現：ablation D
要的是「選股用 ML（`use_ml_composite`），曝險水位由機制決定」——但
`use_regime_weights=True` 會同時把選股邏輯也切換成機制靜態權重，
跟 `use_ml_composite` 要的「選股用 ML」直接衝突，兩個開關綁在一起
沒辦法表達「機制只管曝險、不管選股」這個組合。

**選項**：
A. 維持 `use_regime_weights` 單一開關，ablation D 另外寫一條獨立的
   程式路徑（例如在 `ablation.py` 裡繞過 `build_positions()`，自己
   組裝「ML 分數 × 機制曝險」的部位）——不用動 `quant_layer2.py`，
   但複製一份跟 `build_positions()` 幾乎一樣的再平衡/緩衝區/成本
   邏輯，任何一邊改了容易漏改另一邊，是重複程式碼的風險
B. 把 `use_regime_weights` 拆成兩個獨立開關：`use_regime_factor_weights`
   （只管選股排名依據）與 `use_regime_exposure`（只管曝險水位），
   讓 `build_positions()` 原生支援「ML 選股＋機制曝險」這個組合，
   不用複製邏輯

**選擇**：選項 B。

**為什麼**：兩個開關管的其實是不同層次的決策——選股排名依據（用什麼
分數幫股票排序）跟資金配置比例（曝險縮放）在概念上是正交的，任何一種
排名方法（動態 IC／機制靜態權重／ML）理論上都可以搭配「要不要用機制
曝險縮放」。拆開後 Task 6 需要的四個 ablation 版本都能用同一套
`build_positions()` 表達，不用維護第二份幾乎重複的回測邏輯（`build_positions()`
裡緩衝區、inertia 平滑、交易成本模擬這些邏輯很容易在複製時漏掉或
不小心產生行為差異，這正是本專案一直避免的重複程式碼風險）。

**實作內容**：
- `strategy/quant_layer2.py`：`build_positions()`／`run_pipeline()` 的
  `use_regime_weights` 參數拆成 `use_regime_factor_weights`（原 Task 4a
  功能：機制靜態權重合成因子分數，跟 `use_ml_composite` 互斥）與
  `use_regime_exposure`（原 Task 4b 功能：機制曝險縮放部位規模，
  獨立於選股邏輯，可以搭配任何一種排名方法）
- Ablation D 配置：`use_ml_composite=True` + `use_regime_factor_weights=False`
  + `use_regime_exposure=True`（ML 決定選股排名，機制決定曝險水位，
  兩者互不干擾）
- `is_bull`（是否允許買入新股）跟 renormalize（要不要把權重重新正規化
  回 1）的判斷依據都從 `use_regime_weights` 改成 `use_regime_exposure`
  ——只要曝險縮放在運作，風險控制就交給連續的曝險比例，不再靠 binary
  開關擋買進，避免雙重收緊風險，這個邏輯跟原本 Task 4b 的設計精神
  一致，只是判斷依據換成更精確的開關
- `tests/test_ml_composite.py` 新增 2 項測試：驗證 ablation D 組合
  （ML＋機制曝險）不會丟例外且曝險縮放真的生效；驗證
  `use_regime_exposure=True`＋`use_regime_factor_weights=False` 能重現
  「機制只管曝險、不管選股」的獨立效果。原本測試互斥例外的那項改成
  對 `use_regime_factor_weights` 斷言（語意不變，只是換了參數名稱）

這個最高等級的狀態被設計得很難確認——這是誠實的系統行為，不是 bug，

**選項**：
A. 接受現狀：兩項比例維持「誠實地沒通過」，在 Task 3 報告如實記錄，

B. 進一步調鬆 hysteresis（例如把升級天數從 18 調回 15 或更低），换取
   BULL 比例回升，但會讓切換次數重新超過 40（已實測 up15/down3：切換
   44 次、2016-17 6.1%、2023-24 8.9%，兩個標準只能二選一，無法同時滿足）
C. 重新設計健康分數的門檻或成分（例如降低 BULL 判定的 health 門檻，
   從 60 降到接近實際分佈中位數），讓 BULL 出現頻率貼近任務書預期，
   但這已經是直接調整分類標準去湊比例，屬於本專案一直避免的「調參數
   硬湊結果」

**選擇**：選項 A。

**為什麼**：B 選項證明了 40 次切換與 60% BULL 比例這兩個驗收標準在目前
的系統設計下互斥（switch count 越低，代表遲滯期越長，BULL 越難確認），
魚與熊掌不可兼得，沒有一個「正確」的中間值——選哪個都是主觀取捨，
不是排查能解決的技術問題。C 選項是本專案從一開始就明確拒絕的做法

## 2026-08-17 — inst_flow／margin_usage IC 偏低，複合權重怎麼處理

**狀態：已決定（2026-08-18）— 選項 C**

**問題**：`inst_flow`（IC 0.0034）與 `margin_usage`（IC -0.0039）兩個因子的
20 日前瞻 Spearman IC 都遠低於 0.03 的驗收門檻。

**排查過程（四輪，全部完成，結論一致：不是 bug，是真的沒有訊號）**：

1. **正規化前後對照**（全樣本，無流動性篩選）：-0.0003 vs -0.0024，都偏弱，
   排除「正規化本身造成 IC 偏低」
2. **資料補齊前後對照**：margin_usage 用完整回填後的真實資料（1957 檔）重算，
   仍是 -0.0039，排除「資料不足造成 IC 偏低」
3. **SQL 逐筆核對真實 API**：抽查 5 檔股票（2330/2317/1101/2882/3008）×
   5 個橫跨 2016-2025 的日期，`institutional_investors` 與 `margin_trading`
   兩張表共 50 筆資料，跟即時重打的 FinMind API **全部逐筆一致（50/50）**，
   排除「資料存錯」
4. **短窗口前瞻報酬**：換 5 日／10 日重測，兩個因子在更短窗口下的 IC **都比
   20 日更差**（inst_flow 5日 -0.0013、10日 -0.0015、20日 0.0034；margin_usage
   5日 -0.0065、10日 -0.0081、20日 -0.0039），20 日窗口已經是三者中最好的，
   不是窗口選錯
5. **分年份 IC**（2015-2026）：兩個因子逐年 IC 在正負之間跳動，沒有「某幾年
   訊號很強、被其他年份拉平」的模式——inst_flow 2022 年明顯偏差（-0.0342），
   margin_usage 2019/2023/2024/2025 都是負的、2018/2020-2022 是正的，看起來
   像隨機雜訊，不像被稀釋掉的真訊號（2026 兩者都轉正但樣本只有 46 個交易日，
   數字不可靠，不當作證據）

**結論**：這是誠實的負面結果，不是 bug。兩個因子用目前的定義
（60 日累積買超金額、20 日融資變化率），對未來 5/10/20 日報酬沒有穩定的
線性/單調預測力。

**選項（供使用者選擇，見對話中的白話說明）**：
A. 維持任務書規格的複合權重（inst_flow 30%）
B. 大幅調降 inst_flow 的複合權重，margin_usage 維持排除在外（現狀已排除）
C. 把 inst_flow 也移出主策略複合，兩者都留給 Task 5 的 ML 版本重新評估非線性關係
D. 維持現有的動態 IC 加權機制不變（已經會自動調降低 IC 因子的權重），只調整
   fallback 預設值

**選擇**：選項 C——`inst_flow` 移出主策略複合權重，程式碼保留（不刪除），
與 `margin_usage` 一起留給 Task 5 的 LightGBM 版本重新評估非線性/條件式訊號。

**為什麼**：
1. 訊號在多個獨立角度的檢驗下一致缺席——不是單一測試偶然沒過，而是正規化
   方式、資料完整性、原始資料正確性、短窗口重測、分年份拆解五個互相獨立的
   角度都指向同一個結論，判斷這是真的沒有線性可用的訊號，不是測試方法選錯。
2. 線性排名（cross-sectional IC）方法本身有侷限性，只能抓到單調關係，
   抓不到「連續買超才有效」這類條件式或非線性模式。與其武斷地給一個已知
   在目前方法下無效的訊號分配權重（選項 A/B 都是），不如誠實移出，移交給
   更適合捕捉這類模式的方法（Task 5 的 ML 模型）。
3. 選項 D 的風險是動態加權機制用 IC 絕對值計算權重，雜訊擺動的絕對值不會
   真的趨近於零，等於系統可能還是會給一個純雜訊訊號一些權重，沒有真正
   解決問題。

**後果**：
- `strategy/quant_layer2.py`：`build_positions()` 的 `factor_map`／
  `default_weights` 移除 `inst_flow`；剩餘四因子（momentum/value/rev_yoy/
  low_vol）依實測 20 日 IC 均值相對強弱重新正規化：momentum 0.34 / value
  0.18 / rev_yoy 0.18 / low_vol 0.30（原始 IC：0.038/0.020/0.020/0.033）。
  `build_factors()` 仍計算並回傳 `inst_flow`、`margin_usage`，只是不再進
  複合分數。
- 新增 `reports/factor_negative_findings.md`：正式的負面研究發現報告，
  記錄理論假設、四輪排查方法與結果、結論、後續規劃，準備納入 README 的
  Limitations 章節。
- 移除 inst_flow 前後的策略績效對比、pytest 回歸結果，記錄在對應的 Task
  交付報告中（規則 9 白話格式）。

## 2026-08-17 — 402 配額誤判為「無資料」的 bug

**問題**：margin_trading 全量回填實際上只真正抓到 91/2095 檔（約 4%），但執行
統計顯示「成功 96、失敗 0、跳過 1284」，表面上看起來像是正常的批次跳過，完全
看不出實際上發生了什麼。

**根因**：`_fetch()` 裡 `resp.raise_for_status()` 在檢查 FinMind 回傳的 JSON
`status` 欄位之前，就先對真正的 HTTP 402 狀態碼拋出 `HTTPError`——導致原本設計
的「偵測到 402 就等待配額恢復」那段邏輯從來沒有被執行到，是死碼。402 實際上
被 generic 的 HTTPError 分支接住，只做幾秒鐘的指數退避重試，3 次都失敗就放棄，
把空 DataFrame 回傳給上層，被誤判成「FinMind 確認無資料」，計入「正常跳過」。
`download_institutional.py` 有完全一樣的 bug。

背後還有一個結構性成因：完全沒有機制阻止多個下載 process 同時使用同一個
`FINMIND_TOKEN`——這個帳號等級的配額上限是 600 次/小時，但兩支下載器的限速器
都只在自己的 process 記憶體裡計數，互相看不到對方，兩個 process 同時跑會一起
把共用配額用光。這個問題在診斷過程中實際發生了兩次。

**選項**：
1. **只修 402 判斷邏輯，不加互斥鎖**——治標不治本，下次還是可能有人（或自動化
   排程）不小心同時啟動兩個下載程序，配額衝突會重演
2. **互斥鎖 + 修正 402 判斷 + 402 改成休眠等待自動恢復（不再重試）**——完整修復
   兩個根因
3. **放棄背景自動回填，改成每次都要有人盯著手動跑**——不符合「無人值守長時間
   背景執行」的實際需求，且問題根本沒解決，只是靠人力補償

**選擇**：方案 2（完整修復）。

**為什麼**：根因診斷顯示這是兩個獨立問題疊加（判斷邏輯 bug + 缺乏並發保護），
只修其中一個，另一個下次還是會造成同樣的災情。使用者明確要求要能無人值守
背景執行數小時，方案 1 和 3 都不滿足這個需求。

**後果**：
- 新增 `data_pipeline/download_lock.py`（PID 互斥鎖）、`data_pipeline/finmind_common.py`
  （兩支下載器共用的配額例外類別、心跳、circuit breaker 常數）
- 兩支下載器的順序模式（`workers=1`，也是目前唯一實際使用的模式）現在有完整的
  「402 → 休眠到下個整點 → 自動恢復 → 從 checkpoint 繼續」機制，連續 3 個週期
  仍失敗才放棄
- `download_institutional.py` 的並行模式（`workers>1`）只做了正確性修復（402
  不再被誤判成 skip）+ 簡易 circuit breaker，**沒有**完整跨執行緒的休眠協調——
  已知限制，記錄在 `docs/PROJECT_STATUS.md`，需要無人值守長跑請用 `workers=1`
- 重新跑過一輪完整 backfill 後，Task 1 的 institutional／margin_trading／TAIEX
  三項驗收全部通過
