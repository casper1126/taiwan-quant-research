FinMind 各資料集的真實最早可得日期偵查（Task 3 收尾，線 A）。

**方法**：用真實 API（不是假設或猜官方文件字面意思）對 2330（台積電）、
2317（鴻海）、1101（台泥）三檔龍頭股做小範圍測試查詢，逐步往前推移查詢
窗口，直到查到「窗口內第一筆資料的日期落在窗口中間、不是卡在窗口邊界」
為止——這樣才能確定是真的觸底，不是因為查詢窗口不夠早而被誤判成起點。

**日期**：2026-08-19

## 重要更正：三大法人買賣資料的真實起點不是 2005-01-01

原本的認知（來自「官方文件」）是 `TaiwanStockInstitutionalInvestorsBuySell`
資料庫從 2005-01-01 開始，這是一個沒有實際查證過的假設。**這次直接查證
後發現這個假設是錯的**：

- 對 2005-01-01～2005-12-31、2006/2008/2010 整年分別查詢 2330，全部
  回傳 0 筆資料（`status=200, msg=success, data=[]`——不是錯誤，是真的
  沒有資料）
- 逐步往後找，2012-01-01～2012-12-31 開始出現資料，第一筆是 2012-05-02
- 縮小窗口到 2011-01-01～2012-12-31，用 2330／2317／1101 三檔交叉驗證，
  **三檔股票的第一筆資料日期完全一致：2012-05-02**（3 檔 × 516 筆，
  換算大約每個交易日 3 筆，對應外資／投信／自營商三類法人，資料密度
  正常，不是零星殘缺資料）

**結論：`institutional_investors` 資料集的真實可得起點是 2012-05-02，
不是 2005-01-01。** 這是這次偵查裡最重要的發現，直接影響下面「系統整體
最早起始日」的結論——原本以為推到 2005 年可以拿到完整覆蓋，實際上做
不到，2012-05-02 才是三大法人資料真正的地板。

## 系統整體最早可能起始日

「所有資料集都有完整覆蓋」的起始日，取決於**最晚才有資料的那個資料集**
——也就是三大法人買賣超：

```
系統整體最早起始日 = 2012-05-02
```

（融資融券 2001、月營收 2002、大盤指數 1999、個股股價 1992-1994，
全部比這個日期早，不是限制因素。）

順帶一提，`daily_price` / `daily_valuation` / `monthly_revenue`
三張表**其實已經有 2010-01-01 開始的資料**（Task 1 之前的舊資料，
1662 檔股票），不需要重新下載；真正需要往前補的只有 Task 1 新增的
三張表：`institutional_investors`、`margin_trading`、`market_index`。

## 評估（只評估，不執行）

### 1. 下載量與預估耗時

若把系統起始日從目前的 2015-01-01 往前推到 2012-05-02（多補 2012-05-02
～2015-01-04 約 2.7 年），需要新增下載：

- `institutional_investors`：約 1662 檔股票（`daily_price` 裡已經有
  2015 年以前資料的股票數，2012-2015 年之間沒上市的股票查了也是空的，
  不必浪費額度先篩選）× 1 次 API 呼叫（每次呼叫回傳整段日期範圍，
  不是逐日呼叫）≈ **1662 次呼叫**
- `margin_trading`：同樣約 1662 檔 × 1 次 ≈ **1662 次呼叫**
- `market_index`（TAIEX）：1 次呼叫

**合計約 3325 次 API 呼叫**。現有限速器是 550 次/小時（含 Fix B/C 的
額度耗盡自動休眠機制），預估耗時：

```
3325 / 550 ≈ 6.0 小時（不含 402 額度耗盡休眠、重試的額外時間）
```

實際會比這個數字長一些（heartbeat、少量重試），但用 Task 1 那次
margin_trading 全量回填的實際經驗（約 4 小時 51 分處理 2095 檔 × 1
資料集 ≈ 2095 次呼叫），這次資料量少（3325 次呼叫但只需要 2.7 年
區間，不是 11 年），單次呼叫的回傳資料量小很多、處理更快，預估
**總耗時落在 4-7 小時之間**，可以沿用現有的無人值守休眠恢復機制，
不需要人在旁邊看著。

### 2. 對存活者偏誤（Survivorship Bias）的影響

拉長回測區間到 2012 年，理論上應該讓存活者偏誤問題更嚴重，不是更輕：

- `raw_data/` 目前收錄的股票清單，反映的比較接近「現在還在交易的股票」，
  不是「2012 年當時所有上市股票」的完整名單——如果一檔股票在 2013 年
  下市，而它從來沒被收進 `raw_data/`，那麼往前延伸資料範圍並不會讓它
  自動出現，回測期間拉長只是讓「用倖存股票名單回測更早期間」這件事
  發生的時間更長，偏誤只會被放大，不會被稀釋。
- 這件事本來就已經記錄在 Task 7（`data_pipeline/survivorship.py`）的
  規劃裡，屬於研究誠信模組要正式處理的項目，但既然這次要做決定是否
  延伸資料範圍，這裡先提前示警：**如果真的執行延伸，README 的
  Limitations 章節需要加重這段說明的分量**（不是新增問題，是既有的
  已知限制被拉長的回測期間放大了，必須講清楚 2012-2015 這段的存活者
  偏誤風險比 2015 年之後更高）。

### 3. 對 2016-17 機制判斷空窗的影響

會自動解決，而且margin相當充裕：

- `hmm_detector.py` 需要 504 個交易日（約 2 年）的歷史資料才開始輸出
- 若起始日設在 2012-05-02，504 個交易日後大約落在 **2014 年中**，
  比 2016 年初早了將近一年半到兩年
- 換句話說，只要真的執行這次延伸，2016、2017 兩年會**完整**落在
  HMM 的有效輸出範圍內，不需要任何額外處理或例外邏輯
- **2026-08-21 更新（延伸已執行、已驗證）**：這個預測部分正確、部分
  不完整——2016-17 確實不再是 NaN 空窗（490 個交易日全部有真實的
  health／p_bear／crash_prob 輸出），但「BULL 比例 >60%」這項驗收標準
  依然沒有通過（實測 0%），原因是遲滯機制的升級確認門檻（18 天）跟
  2016-17 實際的訊號連續天數（最長 17 天）差一天沒對上，是機制設計
  本身的特性，不是資料覆蓋問題。完整分析見
  `docs/DECISIONS.md`（2026-08-18～2026-08-21 那筆）與
  `reports/health_score_breadth_divergence.md`。「資料延伸=解決空窗」
  這個預期本身是對的（NaN 空窗確實消失了），但不代表「解決空窗」等於
  「驗收標準會通過」，這裡誠實記錄這個落差，避免以後回來看誤以為
  延伸資料後這項驗收就沒問題了。

### 4. 存活者偏誤曝險時間拉長（2026-08-21 記錄，已執行後的正式提醒）

資料範圍延伸執行後，回測可能涵蓋的期間從原本 2015-2026（11 年）拉長為
**2012-2026（14 年）**。存活者偏誤的曝險時間跟著拉長了 3 年——`raw_data/`
收錄的股票清單仍然只反映「現在還在交易的股票」，不是「2012 年當時所有
上市股票」的完整名單，2012-2015 這段新增的歷史區間，偏誤風險比原本
2015 年之後的區間更高（因為又多了 3 年可能有股票下市卻沒被清單捕捉到
的視窗）。

**影響範圍**：
- Task 7（`data_pipeline/survivorship.py`，存活者偏誤處理模組）的優先度
  因此提高——這件事原本規劃在 Task 7 才正式處理，現在因為實際執行了
  資料延伸，變成一個更急迫、影響更大的已知限制，建議 Task 7 排進度時
  把這個因素納入考量。
- 最終 README 的 Limitations 章節必須提及：本專案的回測結果基於
  2012-2026（或視 Task 使用的實際區間而定）的股票清單，可能存在
  存活者偏誤，且 2012-2015 這段的偏誤風險又比 2015 年之後更高（雙重
  警語，不是單一警語）。
